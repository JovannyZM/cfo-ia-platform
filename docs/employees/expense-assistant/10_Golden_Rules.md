# Reglas de oro

1. La IA ayuda; no inventa.
2. Cuando no sabe, pregunta.
3. Pregunta únicamente lo que falta.
4. No registra hasta tener los datos obligatorios.
5. Pensar como empresa, no como chatbot.
6. Las políticas del negocio valen más que los prompts.
7. Los documentos contables publicados no se modifican.
8. Cancelar conserva historia; borrar la destruye.
9. Toda acción financiera relevante debe ser auditable.
10. La autorización se decide en la API con datos persistidos.
11. Nunca confiar en roles enviados por el frontend.
12. Brain orquesta; los empleados ejecutan.
13. Cada empleado tiene una misión única.
14. Un empleado no realiza el trabajo de otro.
15. Los Workers no controlan el transporte.
16. Los adaptadores no contienen lógica financiera.
17. El contexto conversacional es un expediente, no una variable temporal.
18. Una intención activa no puede degradarse silenciosamente a otra.
19. Cancelación y otras intenciones destructivas tienen prioridad sobre una alta nueva.
20. Nunca actuar sobre una coincidencia ambigua.
21. Cuando hay ambigüedad, ofrecer una selección segura.
22. Persistir los IDs elegibles, no reconstruirlos después.
23. Los cálculos financieros se hacen con código y tipos decimales, no con IA.
24. Las reglas determinísticas deben resolverse sin una llamada adicional de IA.
25. La salida de IA siempre se valida estructuralmente.
26. Las entradas binarias se validan por contenido, no solo por MIME declarado.
27. No conservar datos que el producto no necesita conservar.
28. Una huella puede dar idempotencia sin guardar la evidencia.
29. El aislamiento por Workspace se aplica en cada lectura y escritura.
30. Las pruebas reales tienen prioridad cuando contradicen una suposición de las unitarias.
31. Pruebas verdes no demuestran que el proceso desplegado use el código más reciente.
32. Reiniciar y observar el proceso real forma parte de validar.
33. No declarar éxito sin evidencia real del resultado.
34. `ok=true` importa para una entrega externa.
35. No declarar un Expense registrado si solo existe un borrador o sesión.
36. No simular resultados cuando faltan credenciales.
37. Los errores se sanitizan, pero deben conservar suficiente diagnóstico técnico.
38. Corregir la causa raíz, no acumular frases o parches específicos.
39. Los cambios pequeños rompen menos.
40. Una historia pequeña por vez.
41. Primero misión y límites; después funciones.
42. El costo de oportunidad decide prioridades.
43. Cerrar y graduar un empleado antes de abrir otro.
44. Las mejoras menores pertenecen al backlog de la siguiente versión.
45. Los límites conocidos deben documentarse explícitamente.
46. La semántica del documento vale más que su orden visual.
47. En un documento fiscal, identificar roles antes de extraer nombres.
48. Preservar el valor observable original cuando una normalización pueda cambiar su significado.
49. Reutilizar un flujo probado es preferible a duplicar lógica.
50. La infraestructura debe permitir futuros empleados sin conocerlos por nombre.
